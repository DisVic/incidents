## 1. ОБЩЕЕ ОПИСАНИЕ СИСТЕМЫ

### 1.1. Назначение

IMS (Incident Management System) — это корпоративная веб-система для управления инцидентами в организации. Система предназначена для регистрации, учёта, назначения и контроля решения инцидентов с соблюдением соглашений об уровне сервиса (SLA).

**Основные задачи системы:**
- Централизованная регистрация всех инцидентов
- Автоматическое назначение исполнителей
- Контроль сроков решения (SLA)
- Уведомление участников процесса
- Аналитика и отчётность по эффективности работы
- Управление пользователями и отделами

### 1.2. Основные возможности

**Для всех пользователей:**
- Создание инцидентов
- Просмотр своих инцидентов
- Добавление комментариев
- Получение уведомлений
- Смена пароля, управление профилем

**Для исполнителей:**
- Просмотр инцидентов своего отдела
- Взятие инцидентов в работу
- Решение инцидентов
- Изменение статусов

**Для менеджеров:**
- Управление инцидентами отдела
- Назначение исполнителей
- Просмотр статистики отдела
- Настройка уведомлений

**Для администраторов:**
- Полный доступ ко всем функциям
- Управление пользователями
- Управление отделами
- Настройка статусов, категорий, SLA-политик
- Просмотр полной статистики системы

## 2. АРХИТЕКТУРА СИСТЕМЫ

### 2.1. Общая структура

Система построена по микросервисной архитектуре и состоит из следующих компонентов:

**Frontend (клиентская часть):**
- Одностраничное приложение на Vue 3
- Работает в браузере пользователя
- Общается с backend через REST API
- Хранит состояние в Pinia store
- Маршрутизация через Vue Router

**Backend (серверная часть):**
- API Gateway — единая точка входа
- 4 микросервиса на FastAPI
- PostgreSQL для хранения данных
- Redis для кеширования и очереди задач
- Celery для фоновых задач

**Внешние сервисы:**
- SMTP сервер для отправки email
- Браузер пользователя

### 2.2. Взаимодействие компонентов

**Последовательность запроса:**
1. Пользователь выполняет действие в браузере
2. Frontend отправляет HTTP запрос к API Gateway
3. API Gateway маршрутизирует запрос к нужному сервису
4. Сервис обрабатывает запрос, обращается к базе данных
5. Сервис возвращает ответ через API Gateway
6. Frontend обновляет интерфейс

**Фоновые процессы:**
- Celery Beat запускает задачи каждые 5 минут
- Проверка просрочки SLA
- Проверка эскалации
- Отправка email уведомлений

## 4. БАЗА ДАННЫХ

### 4.1. Общая информация

**СУБД:** PostgreSQL 15  
**Подключение:** Через SQLAlchemy 2.0 (ORM)  
**Расположение:** Отдельный контейнер Docker

### 4.2. Таблицы базы данных

#### Таблица: users (Пользователи)
Хранит информацию о всех пользователях системы.

**Поля:**
- `id` — уникальный идентификатор (первичный ключ)
- `email` — уникальный email для входа
- `password_hash` — хешированный пароль (алгоритм bcrypt)
- `full_name` — ФИО пользователя
- `role_id` — ссылка на таблицу roles (роль пользователя)
- `department_id` — ссылка на таблицу departments (отдел)
- `is_active` — флаг активности (true=активен, false=заблокирован)
- `avatar` — Base64 кодированное изображение аватара (опционально)
- `phone` — номер телефона (опционально)
- `created_at` — дата и время создания записи

#### Таблица: roles (Роли)
Справочник ролей пользователей.

**Поля:**
- `id` — уникальный идентификатор
- `name` — название роли (Admin, Manager, Executor, User)
- `description` — текстовое описание роли

**Значения по умолчанию:**
1. Admin — полный доступ ко всем функциям
2. Manager — управление инцидентами отдела
3. Executor — работа с инцидентами
4. User — создание и просмотр своих инцидентов

#### Таблица: departments (Отделы)
Организационная структура компании.

**Поля:**
- `id` — уникальный идентификатор
- `name` — название отдела (уникальное)
- `description` — описание отдела
- `manager_id` — ссылка на users (руководитель отдела)

#### Таблица: incidents (Инциденты)
Основная таблица для хранения инцидентов.

**Поля:**
- `id` — уникальный идентификатор
- `title` — заголовок инцидента (5-255 символов)
- `description` — подробное описание (мин. 10 символов)
- `status_id` — текущий статус (ссылка на statuses)
- `priority_id` — приоритет (ссылка на priorities)
- `category_id` — категория (ссылка на categories)
- `department_id` — отдел-исполнитель (ссылка на departments)
- `created_by` — инициатор (ссылка на users)
- `assigned_to` — исполнитель (ссылка на users)
- `sla_deadline` — дедлайн по SLA
- `overdue` — флаг просрочки (true/false)
- `created_at` — дата создания
- `assigned_at` — дата назначения
- `taken_at` — дата взятия в работу
- `resolved_at` — дата решения
- `closed_at` — дата закрытия

#### Таблица: statuses (Статусы)
Справочник статусов инцидентов.

**Поля:**
- `id` — уникальный идентификатор
- `name` — название статуса
- `color` — HEX цвет для отображения

**Значения по умолчанию:**
1. Новый (синий #3B82F6)
2. Назначен (фиолетовый #8B5CF6)
3. В работе (жёлтый #EAB308)
4. Решён (зелёный #22C55E)
5. Закрыт (серый #6B7280)

#### Таблица: priorities (Приоритеты)
Справочник приоритетов.

**Поля:**
- `id` — уникальный идентификатор
- `name` — название приоритета
- `sla_hours` — время решения в часах

**Значения по умолчанию:**
1. Критический (4 часа, красный #EF4444)
2. Высокий (8 часов, оранжевый #F97316)
3. Средний (24 часа, синий #3B82F6)
4. Низкий (72 часа, серый #6B7280)

#### Таблица: categories (Категории)
Справочник категорий инцидентов.

**Поля:**
- `id` — уникальный идентификатор
- `name` — название категории
- `description` — описание категории

**Значения по умолчанию:** Сеть, Оборудование, ПО, Доступ, Прочее

#### Таблица: comments (Комментарии)
Комментарии к инцидентам.

**Поля:**
- `id` — уникальный идентификатор
- `incident_id` — ссылка на incidents
- `user_id` — автор комментария (ссылка на users)
- `content` — текст комментария
- `created_at` — дата создания

#### Таблица: incident_history (История изменений)
Журнал всех изменений инцидентов.

**Поля:**
- `id` — уникальный идентификатор
- `incident_id` — ссылка на incidents
- `user_id` — кто изменил (ссылка на users)
- `action` — тип действия (создан, статус изменён, назначен и т.д.)
- `old_values` — старые значения (JSON)
- `new_values` — новые значения (JSON)
- `created_at` — дата изменения

#### Таблица: notifications (Уведомления)
Внутренние уведомления пользователей.

**Поля:**
- `id` — уникальный идентификатор
- `user_id` — получатель (ссылка на users)
- `title` — заголовок уведомления
- `message` — текст уведомления
- `incident_id` — связанный инцидент (опционально)
- `is_read` — флаг прочтения
- `created_at` — дата создания

#### Таблица: notification_settings (Настройки уведомлений)
Персональные настройки уведомлений.

**Поля:**
- `user_id` — пользователь (первичный ключ)
- `incident_created` — настройки для типа (JSON: internal, email)
- `incident_assigned` — настройки для типа
- `status_changed` — настройки для типа
- `incident_resolved` — настройки для типа
- `new_comment` — настройки для типа
- `sla_overdue` — настройки для типа
- `escalation` — настройки для типа
- `priority_changed` — настройки для типа

#### Таблица: sla_policies (SLA политики)
Настройки времени решения по приоритетам.

**Поля:**
- `id` — уникальный идентификатор
- `priority_id` — приоритет (ссылка на priorities)
- `resolution_hours` — время решения в часах
- `description` — описание политики

#### Таблица: escalation_rules (Правила эскалации)
Настройки эскалации инцидентов.

**Поля:**
- `id` — уникальный идентификатор
- `sla_policy_id` — политика SLA (ссылка на sla_policies)
- `level` — уровень эскалации (1, 2)
- `notify_role` — роль для уведомления
- `condition` — условие срабатывания
- `is_active` — флаг активности правила

#### Таблица: password_reset_tokens (Токены сброса пароля)
Временные токены для восстановления пароля.

**Поля:**
- `id` — уникальный идентификатор
- `email` — email пользователя
- `token` — уникальный токен
- `expires_at` — время истечения (1 час после создания)

#### Таблица: attachments (Вложения)
Файлы, прикреплённые к инцидентам.

**Поля:**
- `id` — уникальный идентификатор
- `incident_id` — ссылка на incidents
- `user_id` — кто загрузил
- `filename` — имя файла
- `file_data` — данные файла (Base64)
- `created_at` — дата загрузки

## 5. BACKEND СЕРВИСЫ

### 5.1. API Gateway (порт 8000)

**Назначение:** Единая точка входа для всех клиентских запросов. Маршрутизирует запросы к соответствующим микросервисам.

**Основные функции:**
- Приём HTTP запросов от frontend
- Проверка JWT токенов
- Маршрутизация к сервисам
- Агрегация ответов
- Обработка ошибок

**Группы маршрутов:**
- `/api/auth/*` — перенаправляет в User Service
- `/api/users/*` — перенаправляет в User Service
- `/api/departments/*` — перенаправляет в User Service
- `/api/incidents/*` — перенаправляет в Incident Service
- `/api/sla/*` — перенаправляет в SLA Service
- `/api/notifications/*` — перенаправляет в Notification Service
- `/api/reports/*` — перенаправляет в Incident Service

### 5.2. User Service (порт 8001)

**Назначение:** Управление пользователями, ролями, отделами и аутентификацией.

**Основные функции:**
- Регистрация и вход пользователей
- Генерация и проверка JWT токенов
- Восстановление пароля
- CRUD операции с пользователями
- Управление ролями
- Управление отделами
- Загрузка аватаров
- Смена пароля

**Ключевые endpoints:**
- `POST /auth/login` — вход (email + пароль)
- `POST /auth/logout` — выход
- `POST /auth/refresh` — обновление токена
- `GET /auth/me` — текущий пользователь
- `PUT /auth/password` — смена пароля
- `POST /auth/forgot-password` — запрос сброса пароля
- `POST /auth/reset-password` — сброс по токену
- `GET /users` — список пользователей
- `POST /users` — создание пользователя
- `PUT /users/{id}` — обновление пользователя
- `DELETE /users/{id}` — удаление пользователя
- `PATCH /users/{id}/active` — блокировка/активация
- `POST /users/{id}/avatar` — загрузка аватара
- `GET /departments` — список отделов
- `POST /departments` — создание отдела
- `PUT /departments/{id}` — обновление отдела
- `DELETE /departments/{id}` — удаление отдела

### 5.3. Incident Service (порт 8002)

**Назначение:** Управление инцидентами, комментариями, историей изменений и отчётностью.

**Основные функции:**
- CRUD операции с инцидентами
- Назначение исполнителей
- Изменение статусов и приоритетов
- Добавление комментариев
- Ведение истории изменений
- Формирование отчётов и статистики
- Проверка прав доступа

**Ключевые endpoints:**
- `GET /incidents` — список с фильтрами
- `GET /incidents/{id}` — получение инцидента
- `POST /incidents` — создание инцидента
- `POST /incidents/{id}/take` — взять в работу
- `POST /incidents/{id}/assign` — назначить исполнителя
- `POST /incidents/{id}/resolve` — отметить решённым
- `POST /incidents/{id}/close` — закрыть
- `POST /incidents/{id}/status` — изменить статус
- `POST /incidents/{id}/priority` — изменить приоритет
- `GET /incidents/{id}/history` — история изменений
- `GET /incidents/{id}/comments` — список комментариев
- `POST /incidents/{id}/comments` — добавить комментарий
- `GET /reports/dashboard` — данные дашборда
- `GET /reports/sla-stats` — SLA статистика
- `GET /reports/status-stats` — статистика по статусам
- `GET /reports/activity` — активность
- `GET /reports/executors` — топ исполнителей
- `GET /reports/executors-detailed` — детализация по исполнителям
- `GET /reports/departments` — статистика по отделам
- `GET /reports/sla-analytics` — SLA аналитика
- `GET /reports/overdue-incidents` — просроченные инциденты

### 5.4. SLA Service (порт 8003)

**Назначение:** Управление SLA-политиками, расчёт дедлайнов, мониторинг просрочек, эскалация.

**Основные функции:**
- CRUD SLA-политик
- Расчёт дедлайнов с учётом рабочих часов
- Мониторинг активных инцидентов
- Проверка просрочки SLA
- Проверка эскалации
- Отправка уведомлений о просрочке

**Расчёт дедлайна:**
- Рабочие часы: 9:00–18:00
- Рабочие дни: понедельник–пятница
- Выходные и праздники не учитываются
- Если инцидент создан в нерабочее время, отсчёт начинается с начала следующего рабочего дня

**Ключевые endpoints:**
- `GET /sla/policies` — список политик
- `POST /sla/policies` — создание политики
- `PUT /sla/policies/{id}` — обновление политики
- `DELETE /sla/policies/{id}` — удаление политики

**Фоновые задачи Celery:**
- `check_sla_overdue` — запуск каждые 5 минут
  - Получает все активные инциденты (статусы: Новый, Назначен, В работе)
  - Сравнивает текущее время с дедлайном
  - Устанавливает флаг `overdue = true` при просрочке
  - Отправляет уведомления о просрочке

- `check_escalation` — запуск каждые 5 минут
  - Проверяет процент использования SLA
  - При достижении 80% отправляет предупреждение (Уровень 1)
  - При просрочке отправляет критическое уведомление (Уровень 2)

### 5.5. Notification Service (порт 8004)

**Назначение:** Внутренние уведомления, email-рассылка, настройки уведомлений.

**Основные функции:**

## 8. АУТЕНТИФИКАЦИЯ И АВТОРИЗАЦИЯ

### 8.1. JWT токены

Система использует JWT (JSON Web Tokens) для аутентификации.

**Access token:**
- Срок действия: 15 минут
- Содержит: user_id, email, role_id
- Используется для всех API запросов
- Передаётся в заголовке: `Authorization: Bearer <token>`

**Refresh token:**
- Срок действия: 7 дней
- Хранится в httpOnly cookie
- Используется для получения нового access token
- Автоматическое обновление при истечении access token

### 8.2. Процесс входа

1. Пользователь вводит email и пароль на странице /login
2. Frontend отправляет POST запрос на `/api/auth/login`
3. User Service проверяет credentials в базе данных
4. При успехе генерируются access_token и refresh_token
5. Токены возвращаются клиенту
6. Frontend сохраняет access_token в localStorage
7. Пользователь перенаправляется на /dashboard

### 8.3. Процесс восстановления пароля

1. Пользователь нажимает "Забыли пароль" на странице входа
2. Вводит email на странице /forgot-password
3. Система генерирует уникальный токен сброса
4. Токен сохраняется в базе данных с временем истечения (1 час)
5. На email отправляется письмо со ссылкой: `/reset-password?token=<token>`
6. Пользователь переходит по ссылке
7. Вводит новый пароль на странице /reset-password
8. Система проверяет токен и обновляет пароль
9. Токен удаляется из базы
10. Пользователь перенаправляется на страницу входа

### 8.4. Защита маршрутов

**Router guard проверяет:**
1. Есть ли у пользователя access_token
2. Не истёк ли токен
3. Имеет ли пользователь права для доступа к странице

**При отсутствии прав:**
- Перенаправление на /login (если не авторизован)
- Перенаправление на /dashboard (если нет роли)

## 9. УПРАВЛЕНИЕ ИНЦИДЕНТАМИ

### 9.1. Жизненный цикл инцидента

**Статусы (последовательность):**

1. **Новый** — начальное состояние после создания
   - Инцидент ожидает назначения исполнителя
   - Дедлайн SLA уже рассчитан
   - Видят Manager'ы и Admin'ы отдела

2. **Назначен** — назначен конкретный исполнитель
   - Исполнитель получает уведомление
   - Может взять инцидент в работу

3. **В работе** — исполнитель работает над решением
   - Активен мониторинг SLA
   - Возможна эскалация

4. **Решён** — исполнитель отметил инцидент как решённый
   - Инициатор получает уведомление
   - Ожидает подтверждения закрытия

5. **Закрыт** — инициатор подтвердил решение
   - Инцидент завершён
   - Попадает в архив

### 9.2. Создание инцидента

**Доступ:** Все авторизованные пользователи

**Поля формы:**
- Заголовок (обязательно, 5-255 символов)
- Описание (обязательно, минимум 10 символов)
- Категория (обязательно, выбор из справочника)
- Приоритет (обязательно, выбор из справочника)
- Отдел-исполнитель (обязательно, выбор из справочника)

**Автоматически при создании:**
- Статус устанавливается в "Новый"
- Дата создания = текущее время
- Инициатор = текущий пользователь
- Рассчитывается дедлайн SLA (на основе приоритета)
- Создаётся запись в истории: "Инцидент создан"
- Отправляются уведомления: Manager отдела, Admin, Executor'ы отдела

### 9.3. Фильтры и поиск

**Доступные фильтры:**
- По статусу (множественный выбор)
- По приоритету (множественный выбор)
- По категории (множественный выбор)
- По отделу (одиночный выбор)
- По статусу SLA: просроченные / близкие к дедлайну (>80%) / в норме
- Поиск по заголовку (частичное совпадение)

**Сортировка:**
- По дате создания (новые/старые)
- По дедлайну SLA (раньше/позже)
- По приоритету (высокий/низкий)
- По заголовку (А-Я / Я-А)

**Пагинация:**
- Варианты: 20, 50, 100 записей на страницу
- Переключение между страницами
- Отображение: "Показано X-Y из Z"

### 9.4. Действия с инцидентами

**Взять в работу:**
- Доступно: Executor, Manager, Admin
- Требование: статус "Новый" или "Назначен", нет исполнителя
- Результат: статус "В работе", assigned_to = текущий пользователь, taken_at = текущее время

**Назначить исполнителя:**
- Доступно: Manager, Admin
- Требование: статус "Новый" или "Назначен"
- Результат: assigned_to = выбранный пользователь, assigned_at = текущее время, статус "Назначен"

**Изменить статус:**
- Доступно: Executor, Manager, Admin
- Требование: обязательный комментарий
- Результат: запись в истории, уведомление участников

**Изменить приоритет:**
- Доступно: Manager, Admin
- Результат: пересчёт дедлайна SLA, запись в истории, уведомление

**Отметить как решённый:**
- Доступно: Executor, Manager, Admin
- Требование: обязательный комментарий о решении
- Результат: статус "Решён", resolved_at = текущее время, уведомление инициатора

**Закрыть инцидент:**
- Доступно: User (инициатор), Manager, Admin
- Требование: статус "Решён"
- Результат: статус "Закрыт", closed_at = текущее время

**Удалить инцидент:**
- Доступно: Admin
- Требование: подтверждение удаления
- Результат: физическое удаление из базы (каскадно: комментарии, история, вложения)

## 10. SLA И ЭСКАЛАЦИЯ

### 10.1. SLA-политики

**Настройка:** Admin в разделе Настройки системы

**Политики по умолчанию:**
- Критический приоритет: 4 часа
- Высокий приоритет: 8 часов
- Средний приоритет: 24 часа
- Низкий приоритет: 72 часа

**Расчёт дедлайна:**
- Учитываются только рабочие часы: 9:00–18:00
- Учитываются только рабочие дни: понедельник–пятница
- Выходные (суббота, воскресенье) не учитываются
- Праздничные дни не учитываются (требуется отдельный календарь)

**Пример расчёта:**
- Инцидент создан: Пятница, 17:00
- Приоритет: Высокий (8 часов)
- Дедлайн: Следующая Среда, 17:00
  - Пятница 17:00–18:00 = 1 час
  - Понедельник 9:00–18:00 = 9 часов (но нужно только 7)
  - Итого: Понедельник 16:00

### 10.2. Мониторинг SLA

**Фоновая задача:** `check_sla_overdue`
**Частота запуска:** каждые 5 минут
**Выполняет:** Celery Worker

**Алгоритм:**
1. Получить все активные инциденты (статусы: Новый, Назначен, В работе)
2. Для каждого инцидента:
   - Сравнить текущее время с дедлайном
   - Если текущее время > дедлайна: установить `overdue = true`
   - Отправить уведомление о просрочке
3. Обновить базу данных

**Визуальная индикация во frontend:**
- Зелёный цвет: осталось более 40% времени SLA
- Жёлтый цвет: осталось от 10% до 40% времени SLA
- Красный цвет: осталось менее 10% времени SLA
- Красный с текстом "ПРОСРОЧЕН": дедлайн истёк (overdue = true)

### 10.3. Эскалация

**Фоновая задача:** `check_escalation`
**Частота запуска:** каждые 5 минут

**Уровень 1 (Предупреждение):**
- Условие: использовано ≥80% времени SLA
- Получатели: Manager отдела, Admin
- Тип уведомления: Внутреннее + Email
- Текст: "Инцидент #ID близок к просрочке SLA"

**Уровень 2 (Критическое):**
- Условие: `overdue = true`
- Получатели: Admin
- Тип уведомления: Внутреннее + Email (критическое)
- Текст: "Инцидент #ID ПРОСРОЧЕН! Требуется немедленное вмешательство"

**Правила эскалации:**
- Настраиваются через таблицу `escalation_rules`
- Поля: уровень, роль для уведомления, условие, активность
- Могут быть изменены Admin через API

## 11. УВЕДОМЛЕНИЯ

### 11.1. Внутренние уведомления

**Где отображаются:**
- Колокольчик в хедере (верхняя панель)
- Счётчик непрочитанных (красный бейдж)
- Выпадающий список последних уведомлений (при клике на колокольчик)

**Функции:**
- Пометить как прочитанное (по одному)
- Прочитать все (массово)
- Переход к инциденту (при клике на уведомление)

- Новый комментарий
- Просрочка SLA

## 12. ДАШБОРД И СТАТИСТИКА

### 12.1. Дашборд (Manager, Admin)

**Фильтры:**
- Период: текущий месяц, прошлый месяц, квартал, год, свой период
- Отдел: только для Admin (выбор из списка)

**Основные метрики (карточки):**
- Всего инцидентов — общее количество за период
- Новые — количество инцидентов со статусом "Новый"
- В работе — количество инцидентов со статусом "В работе"
- Решённые — количество инцидентов со статусом "Решён"
- Просроченные — количество инцидентов с `overdue = true`

**Графики:**

1. **SLA-статистика (круговая диаграмма)**
   - Соблюдён SLA (зелёный)
   - Близко к дедлайну (жёлтый)
   - Просрочен (красный)

2. **Распределение по статусам (круговая диаграмма)**
   - Сектора: Новый, Назначен, В работе, Решён, Закрыт

3. **Активность за 14 дней (столбчатая диаграмма)**
   - Ось X: дни (последние 14 дней)
   - Ось Y: количество инцидентов
   - Столбцы: созданные, решённые

4. **Топ исполнителей за 30 дней (горизонтальная диаграмма)**
   - Список исполнителей
   - Количество решённых инцидентов
   - Среднее время решения

**Детализация (аккордеоны):**

1. **По исполнителям:**
   - Назначено
   - Решено
   - Среднее время решения
   - Просрочено
   - % соблюдения SLA

2. **По отделам (только Admin):**
   - Аналогично по исполнителям, но в разрезе отделов

3. **SLA-аналитика:**
   - Среднее время решения по приоритетам
   - Распределение просрочек по категориям
   - Динамика соблюдения SLA по месяцам

4. **История просроченных инцидентов:**
   - Таблица последних просроченных инцидентов
   - ID, заголовок, исполнитель, дедлайн, текущее время

### 12.2. Статистика пользователя

**Страница:** `/users/:id/stats`
**Доступ:** Manager, Admin

**Метрики:**
- Назначено инцидентов
- Решено инцидентов
- В работе
- Просрочено
- Среднее время решения (часы/дни)
- % соблюдения SLA

**Графики:**
- Активность по дням (выбранный период)
- Распределение по статусам
- Топ категорий (по количеству)

**Таблица инцидентов:**
- Заголовок (ссылка на инцидент)
- Статус (бейдж)
- Приоритет (бейдж)
- Дедлайн SLA (с подсветкой просрочки)
- Время решения (часы/дни)
- SLA статус (OK / Просрочен)

**Фильтры периода:**
- Месяц (текущий)
- Квартал (текущий)
- Год (текущий)
- Конкретный месяц (выбор из списка)
- Свой период (выбор дат от и до)

## 13. НАСТРОЙКИ СИСТЕМЫ

### 13.1. Статусы инцидентов

**Доступ:** Admin
**Страница:** /settings (вкладка "Статусы")

**Функции:**
- Просмотр списка статусов
- Добавление нового статуса
- Редактирование существующего
- Удаление (если не используется)

**Поля статуса:**
- Название (обязательно, уникальное)
- Цвет (выбор цвета или HEX код)

**Статусы по умолчанию:**
1. Новый (синий)
2. Назначен (фиолетовый)
3. В работе (жёлтый)
4. Решён (зелёный)
5. Закрыт (серый)

### 13.2. Категории инцидентов

**Доступ:** Admin
**Страница:** /settings (вкладка "Категории")

**Функции:**
- Просмотр списка категорий
- Добавление новой категории
- Редактирование существующей
- Удаление (если не используется)

**Поля категории:**
- Название (обязательно, уникальное)
- Описание (опционально)

**Категории по умолчанию:**
1. Сеть
2. Оборудование
3. ПО
4. Доступ
5. Прочее

### 13.3. SLA-политики

**Доступ:** Admin
**Страница:** /settings (вкладка "SLA-политики")

**Функции:**
- Просмотр списка политик
- Редактирование времени решения
- Добавление описания

**Поля политики:**
- Приоритет (из справочника, нельзя изменить)
- Время на решение (часы, обязательно)
- Описание (опционально)

**Политики по умолчанию:**
- Критический: 4 часа
- Высокий: 8 часов
- Средний: 24 часа
- Низкий: 72 часа
