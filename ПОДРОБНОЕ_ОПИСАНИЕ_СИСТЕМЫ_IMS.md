## 1. ВВЕДЕНИЕ И ОБЗОР СИСТЕМЫ

### 1.1. Назначение системы

IMS (Incident Management System) представляет собой комплексную корпоративную веб-систему, предназначенную для автоматизации процессов управления инцидентами в организации любого масштаба. Система охватывает полный жизненный цикл инцидента — от момента его регистрации инициатором до финального закрытия и архивации.

**Ключевые бизнес-задачи, решаемые системой:**

1. **Централизованная регистрация инцидентов**
   - Все инциденты фиксируются в единой системе
   - Исключается потеря заявок
   - Формируется полная история по каждому инциденту

2. **Автоматическое распределение нагрузки**
   - Инциденты автоматически направляются в соответствующие отделы
   - Менеджеры могут назначать конкретных исполнителей
   - Исполнители могут самостоятельно брать инциденты в работу

3. **Контроль сроков решения (SLA)**
   - Для каждого приоритета установлено нормативное время решения
   - Система автоматически рассчитывает дедлайны с учётом рабочих часов
   - При приближении к дедлайну и при просрочке отправляются уведомления
   - Руководство видит статистику соблюдения SLA по сотрудникам и отделам

4. **Прозрачность процесса**
   - Все участники видят текущий статус инцидента
   - История изменений фиксируется полностью
   - Комментарии позволяют вести диалог по инциденту

5. **Аналитика и отчётность**
   - Дашборд с ключевыми метриками
   - Статистика по исполнителям и отделам
   - Выявление проблемных зон и узких мест

6. **Уведомление участников**
   - Автоматические уведомления о важных событиях
   - Настройка типов уведомлений для каждого пользователя
   - Поддержка внутренних уведомлений и email

### 1.2. Целевая аудитория системы

**Инициаторы (User):**
- Сотрудники организации, не являющиеся техническими специалистами
- Сталкиваются с проблемами в работе ИТ-систем, оборудования, ПО
- Нуждаются в быстром решении своих проблем
- Требуют простой интерфейс создания заявки и возможность отслеживать статус

**Исполнители (Executor):**
- Технические специалисты (ИТ-отдел, служба поддержки)
- Непосредственно работают над решением инцидентов
- Нуждаются в удобном инструменте управления своей рабочей нагрузкой
- Требуют возможности видеть все назначенные инциденты, фильтровать, сортировать

**Менеджеры (Manager):**
- Руководители отделов и служб
- Контролируют работу своих подчинённых
- Распределяют нагрузку между исполнителями
- Требуют инструменты мониторинга и аналитики
- Отвечают за соблюдение SLA в своём отделе

**Администраторы (Admin):**
- Администраторы системы
- Управляют пользователями и структурой организации
- Настраивают параметры системы (статусы, категории, SLA)
- Имеют полный доступ ко всем функциям
- Отвечают за корректную работу системы в целом

### 1.3. Основные возможности системы

**Функционал для всех пользователей:**
- Регистрация в системе (через администратора)
- Вход по email и паролю
- Восстановление пароля через email
- Просмотр и редактирование профиля
- Загрузка аватара
- Создание инцидентов
- Просмотр своих инцидентов
- Добавление комментариев к инцидентам
- Получение уведомлений (внутренние и email)
- Настройка типов уведомлений (для Manager и Admin)

**Функционал для исполнителей:**
- Просмотр инцидентов своего отдела
- Фильтрация и сортировка инцидентов
- Взятие инцидентов в работу
- Изменение статусов инцидентов
- Отметка о решении инцидента
- Добавление комментариев
- Просмотр истории изменений

**Функционал для менеджеров:**
- Все функции исполнителя
- Назначение исполнителей на инциденты
- Просмотр статистики отдела
- Дашборд с метриками
- Настройка уведомлений
- Просмотр статистики по сотрудникам

**Функционал для администраторов:**
- Все функции менеджера
- Управление пользователями (создание, редактирование, удаление, блокировка)
- Управление отделами (создание, редактирование, удаление)
- Настройка статусов инцидентов
- Настройка категорий инцидентов
- Настройка SLA-политик
- Просмотр полной статистики системы
- Удаление инцидентов

### 1.4. Ключевые понятия системы

**Инцидент** — это зафиксированное в системе событие, требующее решения. Каждый инцидент имеет заголовок, описание, приоритет, категорию, статус, отдел-исполнитель, инициатора и (опционально) исполнителя.

**SLA (Service Level Agreement)** — соглашение об уровне сервиса. Определяет нормативное время решения инцидента в зависимости от его приоритета. Нарушение SLA фиксируется и влияет на статистику.

**Эскалация** — процесс уведомления руководства о проблемах с инцидентом. Срабатывает при приближении к дедлайну (80% SLA) и при просрочке.

**Статус инцидента** — текущее состояние инцидента в процессе обработки. Определяет, какие действия доступны с инцидентом и кто может их выполнять.

**Приоритет инцидента** — степень важности инцидента. Влияет на время решения по SLA и на порядок обработки.

**Категория инцидента** — классификация инцидента по типу проблемы. Используется для аналитики и распределения по отделам.

## 2. ДЕТАЛЬНАЯ АРХИТЕКТУРА СИСТЕМЫ

### 2.1. Общая архитектура

Система построена по микросервисной архитектуре с разделением ответственности между компонентами. Такое разделение позволяет масштабировать отдельные части системы независимо друг от друга, упрощает поддержку и развитие.

**Уровни архитектуры:**

**Уровень 1: Клиентский уровень (Frontend)**
- Веб-браузер пользователя
- Одностраничное приложение (SPA) на Vue 3
- Работает полностью на стороне клиента
- Общается с сервером через HTTP/REST API
- Хранит состояние приложения в браузере
- Обрабатывает пользовательский ввод и отображает данные

**Уровень 2: Уровень API (API Gateway)**
- Единая точка входа для всех запросов
- Принимает HTTPS запросы от frontend
- Проверяет JWT токены аутентификации
- Маршрутизирует запросы к соответствующим микросервисам
- Возвращает ответы клиенту
- Обрабатывает ошибки и возвращает корректные HTTP статусы

**Уровень 3: Сервисный уровень (Микросервисы)**
- User Service — сервис пользователей и аутентификации
- Incident Service — сервис инцидентов и отчётности
- SLA Service — сервис SLA и эскалации
- Notification Service — сервис уведомлений
- Каждый сервис независим и отвечает за свою область
- Сервисы общаются между собой при необходимости

**Уровень 4: Уровень данных**
- PostgreSQL — основное хранилище данных
- Redis — кеширование и очередь задач
- Все сервисы работают с единой базой данных
- Данные нормализованы и связаны внешними ключами

**Уровень 5: Фоновые процессы**
- Celery Worker — выполнение фоновых задач
- Celery Beat — планировщик задач
- Redis Broker — очередь сообщений
- Задачи: мониторинг SLA, эскалация, email рассылка

**Уровень 6: Внешние сервисы**
- SMTP сервер — отправка email уведомлений
- Браузер пользователя — отображение интерфейса

### 2.2. Поток данных в системе

**Типичный запрос пользователя:**

1. Пользователь открывает браузер и переходит на адрес системы
2. Frontend приложение загружается в браузере
3. Пользователь вводит email и пароль, нажимает "Войти"
4. Frontend отправляет POST запрос на `/api/auth/login`
5. API Gateway принимает запрос, проверяет формат
6. API Gateway перенаправляет запрос в User Service
7. User Service ищет пользователя в базе по email
8. User Service проверяет хеш пароля (bcrypt)
9. При успехе генерируются JWT токены (access + refresh)
10. Токены возвращаются через API Gateway во frontend
11. Frontend сохраняет токены в localStorage
12. Frontend перенаправляет пользователя на /dashboard
13. Последующие запросы включают access_token в заголовке

**Фоновый процесс мониторинга SLA:**

1. Celery Beat запускает задачу `check_sla_overdue` каждые 5 минут
2. Celery Worker получает задачу из очереди Redis
3. Worker подключается к базе данных через SLA Service
4. Получает список активных инцидентов (Новый, Назначен, В работе)
5. Для каждого инцидента сравнивает текущее время с дедлайном
6. Если время вышло — устанавливает флаг overdue = true
7. Создаёт запись в таблице notifications для получателей
8. Отправляет email через Notification Service
9. Обновляет базу данных
10. Задача завершена, Worker ожидает следующую

### 2.3. Взаимодействие сервисов

**API Gateway + User Service:**
- Все запросы аутентификации идут в User Service
- CRUD пользователей обрабатывается в User Service
- Управление отделами — тоже User Service
- API Gateway только маршрутизирует, не обрабатывает

**API Gateway + Incident Service:**
- Все запросы по инцидентам идут в Incident Service
- Создание, чтение, обновление инцидентов
- Комментарии и история изменений
- Отчёты и статистика (дашборд, метрики)

**API Gateway + SLA Service:**
- CRUD SLA-политик
- Расчёт дедлайнов при создании инцидента
- Пересчёт дедлайна при изменении приоритета

**API Gateway + Notification Service:**
- Получение списка уведомлений
- Отметка прочитанными
- Настройки уведомлений
- Отправка email (через SMTP)

**Межсервисное взаимодействие:**

1. **Incident Service → Notification Service**
   - При создании инцидента: отправить уведомления
   - При назначении: уведомить исполнителя
   - При изменении статуса: уведомить участников
   - При новом комментарии: уведомить участников

2. **Incident Service → SLA Service**
   - При создании инцидента: рассчитать дедлайн
   - При изменении приоритета: пересчитать дедлайн

3. **SLA Service → Notification Service**
   - При эскалации Уровень 1: предупредить Manager
   - При эскалации Уровень 2: уведомить Admin

4. **User Service → Notification Service**
   - При смене пароля: уведомить пользователя
   - При создании пользователя: отправить данные для входа

### 2.4. Масштабирование системы

**Горизонтальное масштабирование:**
- Каждый микросервис может быть запущен в нескольких экземплярах
- API Gateway распределяет нагрузку между экземплярами
- База данных PostgreSQL поддерживает репликацию
- Redis кластеризуется для высокой доступности

**Вертикальное масштабирование:**
- Увеличение ресурсов контейнеров (CPU, RAM)
- Увеличение параметров PostgreSQL (shared_buffers, connections)
- Настройка пулов соединений для каждого сервиса

**Оптимизация производительности:**
- Кеширование частых запросов в Redis
- Индексы на часто используемых полях БД
- Пагинация больших списков
- Асинхронная отправка email

#### src/stores/auth.js
```javascript
// Pinia store для аутентификации
import { defineStore } from 'pinia'
import axios from 'axios'

export const useAuthStore = defineStore('auth', {
  state: () => ({
    user: null,           // Данные текущего пользователя
    token: localStorage.getItem('access_token') || null,
    refreshToken: localStorage.getItem('refresh_token') || null
  }),
  
  getters: {
    isAuthenticated: (state) => !!state.token,
    isAdmin: (state) => state.user?.role_name === 'Admin',
    isManager: (state) => state.user?.role_name === 'Manager',
    isExecutor: (state) => state.user?.role_name === 'Executor'
  },
  
  actions: {
    async login(email, password) {
      const response = await axios.post('/api/auth/login', { email, password })
      this.token = response.data.access_token
      this.refreshToken = response.data.refresh_token
      this.user = response.data.user
      localStorage.setItem('access_token', this.token)
      localStorage.setItem('refresh_token', this.refreshToken)
    },
    
    logout() {
      this.user = null
      this.token = null
      this.refreshToken = null
      localStorage.removeItem('access_token')
      localStorage.removeItem('refresh_token')
    },
    
    async refreshToken() {
      const response = await axios.post('/api/auth/refresh', {
        refresh_token: this.refreshToken
      })
      this.token = response.data.access_token
      localStorage.setItem('access_token', this.token)
    }
  }
})
```

## 4. БАЗА ДАННЫХ — ПОЛНОЕ ОПИСАНИЕ

### 4.1. Общая информация

**СУБД:** PostgreSQL версии 15 или выше  
**Движок хранения:** InnoDB  
**Кодировка:** UTF-8  
**Подключение:** Через SQLAlchemy 2.0 ORM  
**Пул соединений:** 10-20 соединений на сервис

### 4.2. Детальное описание таблиц

#### Таблица: users

**Назначение:** Хранение информации о всех пользователях системы, включая данные для аутентификации, профильную информацию и связи с ролями и отделами.

**Структура полей:**

| Поле | Тип данных | Ограничения | Описание |
|------|------------|-------------|----------|
| id | INTEGER | PRIMARY KEY, AUTO INCREMENT | Уникальный идентификатор пользователя. Генерируется автоматически при создании. |
| email | VARCHAR(255) | UNIQUE, NOT NULL | Email адрес пользователя. Используется для входа в систему. Должен быть уникальным во всей системе. |
| password_hash | VARCHAR(255) | NOT NULL | Хешированный пароль. Хранится хеш, созданный алгоритмом bcrypt с солью. Исходный пароль не хранится. |
| full_name | VARCHAR(255) | NOT NULL | Полное имя пользователя (ФИО). Отображается в интерфейсе, в уведомлениях, в списках. |
| role_id | INTEGER | FOREIGN KEY → roles.id, NOT NULL | Ссылка на роль пользователя. Определяет права доступа. Значения: 1=Admin, 2=Manager, 3=Executor, 4=User. |
| department_id | INTEGER | FOREIGN KEY → departments.id, NULL | Ссылка на отдел пользователя. NULL если пользователь не принадлежит отделу. |
| is_active | BOOLEAN | DEFAULT TRUE | Флаг активности пользователя. FALSE = пользователь заблокирован и не может войти. |
| avatar | TEXT | NULL | Base64 кодированное изображение аватара. Хранится непосредственно в БД. Максимальный размер 500KB. |
| phone | VARCHAR(50) | NULL | Номер телефона для связи. Опциональное поле. |
| created_at | TIMESTAMP | DEFAULT NOW() | Дата и время создания записи. Устанавливается автоматически при создании пользователя. |

**Индексы:**
- PRIMARY KEY на id
- UNIQUE на email
- INDEX на role_id (для быстрого поиска по роли)
- INDEX на department_id (для поиска по отделу)
- INDEX на is_active (для фильтрации активных)

**Связи:**
- MANY-TO-ONE с roles (многие пользователи к одной роли)
- MANY-TO-ONE с departments (многие пользователи к одному отделу)
- ONE-TO-MANY с incidents (один пользователь создаёт много инцидентов как инициатор)
- ONE-TO-MANY с incidents (один пользователь исполняет много инцидентов как assigned_to)
- ONE-TO-MANY с comments (один пользователь пишет много комментариев)
- ONE-TO-MANY с notifications (один пользователь получает много уведомлений)

**Бизнес-правила:**
- Email должен быть уникальным
- Пароль должен быть захеширован перед сохранением
- Нельзя удалить последнего активного Admin
- При блокировке исполнителя его активные инциденты сбрасываются в статус "Новый"

- INDEX на priority_id (для сортировки по приоритету)
- INDEX на department_id (для поиска по отделу)
- INDEX на created_by (для поиска своих инцидентов)
- INDEX на assigned_to (для поиска назначенных)
- INDEX на sla_deadline (для поиска просроченных)
- INDEX на created_at (для сортировки по дате)
- COMPOSITE INDEX на (status_id, assigned_to) для частых запросов

**Бизнес-правила:**
- При создании статус автоматически устанавливается в "Новый"
- При создании рассчитывается sla_deadline на основе приоритета
- При назначении исполнителя устанавливается assigned_at
- При взятии в работу устанавливается taken_at
- При решении устанавливается resolved_at
- При закрытии устанавливается closed_at
- При просрочке (overdue = TRUE) отправляется уведомление

### 5.1. API Gateway (порт 8000)

**Технологии:** FastAPI, Uvicorn, httpx

**Основная задача:** Быть единой точкой входа для всех клиентских запросов и маршрутизировать их к соответствующим микросервисам.

**Детальный функционал:**

**1. Приём и валидация запросов:**
- Принимает HTTPS запросы от frontend приложения
- Проверяет Content-Type заголовок
- Валидирует JSON body запроса
- Проверяет наличие и формат JWT токена в заголовке Authorization

**2. Аутентификация:**
- Извлекает JWT токен из заголовка `Authorization: Bearer <token>`
- Проверяет валидность токена (срок действия, подпись)
- Извлекает user_id и role_id из payload токена
- Добавляет информацию о пользователе в заголовки для сервисов

**3. Маршрутизация:**
- Анализирует путь запроса (URL path)
- Определяет целевой сервис по префиксу пути
- Перенаправляет запрос с сохранением метода, headers и body
- Возвращает ответ от сервиса клиенту

**Таблица маршрутизации:**

| Префикс пути | Целевой сервис | Порт |
|--------------|----------------|------|
| /api/auth/* | User Service | 8001 |
| /api/users/* | User Service | 8001 |
| /api/departments/* | User Service | 8001 |
| /api/incidents/* | Incident Service | 8002 |

| /api/reports/* | Incident Service | 8002 |
| /api/sla/* | SLA Service | 8003 |
| /api/notifications/* | Notification Service | 8004 |

**4. Обработка ошибок:**
- Ловит исключения от сервисов
- Преобразует в стандартный формат ошибок
- Возвращает корректные HTTP статус коды
- Логирует ошибки для отладки

**5. Логгирование:**
- Логирует все входящие запросы
- Записывает время обработки
- Сохраняет IP адрес пользователя
- Логирует ошибки с деталями

**Пример кода маршрутизации:**
```python
@app.api_route("/api/{service_path:path}", methods=["GET", "POST", "PUT", "DELETE", "PATCH"])
async def proxy_request(service_path: str, request: Request):
    # Определение сервиса по пути
    if service_path.startswith("auth/") or service_path.startswith("users/"):
        target_service = USER_SERVICE_URL
    elif service_path.startswith("incidents/"):
        target_service = INCIDENT_SERVICE_URL
    # ...
    
    # Проксирование запроса
    async with httpx.AsyncClient() as client:
        response = await client.request(
            method=request.method,
            url=f"{target_service}/api/{service_path}",
            headers=dict(request.headers),
            content=await request.body()
        )
    
    return Response(response.content, status_code=response.status_code)
```

### 5.4. SLA Service (порт 8003)

**Технологии:** FastAPI, SQLAlchemy, datetime

**Основная задача:** Расчёт дедлайнов с учётом рабочих часов, мониторинг просрочек.

**Детальный функционал:**

**1. Расчёт дедлайна:**
```python
def calculate_sla_deadline(created_at: datetime, priority_id: int) -> datetime:
    # Получение SLA часов для приоритета
    policy = get_sla_policy(priority_id)
    hours_to_add = policy.resolution_hours
    
    current_time = created_at
    
    # Если вне рабочих часов, переносим на начало следующего рабочего дня
    if not is_business_hours(current_time):
        current_time = next_business_day_start(current_time)
    
    # Добавляем рабочие часы
    while hours_to_add > 0:
        if is_weekend(current_time):
            current_time = next_monday_start(current_time)
            continue
        
        # Оставшееся время в текущем рабочем дне
        end_of_day = current_time.replace(hour=18, minute=0, second=0)
        hours_remaining_today = (end_of_day - current_time).seconds / 3600
        
        if hours_to_add <= hours_remaining_today:
            current_time += timedelta(hours=hours_to_add)
            hours_to_add = 0
        else:
            hours_to_add -= hours_remaining_today
            current_time = next_business_day_start(current_time)
    
    return current_time
```

**2. Проверка рабочего времени:**
```python
def is_business_hours(dt: datetime) -> bool:
    # Проверка дня недели (0=Пн, 6=Вс)
    if dt.weekday() >= 5:  # Суббота или Воскресенье
        return False
    
    # Проверка времени (9:00 - 18:00)
    if dt.hour < 9 or dt.hour >= 18:
        return False
    
    # Проверка праздников (требуется отдельная таблица)
    if is_holiday(dt.date()):
        return False
    
    return True
```

```python
def send_email(to: str, subject: str, body: str):
    import smtplib
    from email.mime.text import MIMEText
    
    msg = MIMEText(body, 'html')
    msg['Subject'] = subject
    msg['From'] = SMTP_FROM
    msg['To'] = to
    
    server = smtplib.SMTP(SMTP_HOST, SMTP_PORT)
    server.starttls()
    server.login(SMTP_USER, SMTP_PASSWORD)
    server.send_message(msg)
    server.quit()
```
