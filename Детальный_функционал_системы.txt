
# ДЕТАЛЬНОЕ ОПИСАНИЕ ФУНКЦИОНАЛА СИСТЕМЫ
## Корпоративная система управления инцидентами

---

## 1. МОДУЛЬ: УПРАВЛЕНИЕ ИНЦИДЕНТАМИ

### 1.1. Создание инцидента
**Доступ:** Все роли (User, Executor, Manager, Admin)

**Форма создания включает:**
- Заголовок (обязательное поле, 5-255 символов)
- Описание проблемы (обязательное, текстовое поле, минимум 10 символов)
- Категория (выпадающий список: Сеть, Оборудование, ПО, Доступ, Прочее)
- Приоритет (выбор: Низкий, Средний, Высокий, Критический)
- **Отдел-исполнитель** (выпадающий список отделов, обязательное поле)
- Прикрепление файлов (drag-n-drop или кнопка выбора, до 5 файлов по 10МБ)

**Логика работы:**
1. Пользователь заполняет форму и нажимает "Создать"
2. Система автоматически присваивает уникальный ID
3. Устанавливает статус "Новый"
4. Фиксирует дату/время создания
5. Назначает инициатора (текущий пользователь)
6. **Назначает отдел-исполнитель** (выбранный пользователем)
7. Рассчитывает дедлайн SLA: берёт из таблицы SlaPolicy время для выбранного приоритета и прибавляет к текущему времени
8. Создаёт первую запись в IncidentHistory: "Инцидент создан и направлен в отдел [Название]"
9. Отправляет уведомления **всем сотрудникам отдела** (Email + Telegram + внутреннее)
10. Перенаправляет на страницу просмотра созданного инцидента

**Валидация:**
- Заголовок не пустой, длина 5-255 символов
- Описание минимум 10 символов
- Категория, приоритет и отдел обязательны
- Файлы: разрешённые форматы (jpg, png, pdf, doc, docx, txt, log), размер до 10МБ каждый

---

### 1.2. Просмотр списка инцидентов
**Доступ:** Все роли (с разной видимостью)

**Табличное представление:**

Колонки таблицы:
- ID (кликабельный для перехода)
- Заголовок (до 50 символов, остальное обрезается с "...")
- Категория
- Приоритет (цветной бэдж: Критический-красный, Высокий-оранжевый, Средний-синий, Низкий-серый)
- Статус (цветные бэджи)
- **Отдел** (название отдела-исполнителя)
- Инициатор (ФИО)
- Исполнитель (ФИО или "Не назначен")
- Дата создания
- Дедлайн SLA (с цветовым индикатором времени)

**Фильтрация:**
- По статусу: чекбоксы (можно выбрать несколько)
- По приоритету: чекбоксы
- По категории: выпадающий список с множественным выбором
- **По отделу:** выпадающий список
- По исполнителю: выпадающий список (только для Manager/Admin)
- По дате создания: два поля "с" и "по" с календарём
- По статусу SLA: радиокнопки (все / только просроченные / близкие к просрочке)

**Сортировка (клик по заголовку колонки):**
- По ID (возрастание/убывание)
- По дате создания
- По приоритету (по уровню)
- По дедлайну SLA

**Пагинация:**
- 20 записей на страницу по умолчанию
- Выбор: 20 / 50 / 100 записей
- Навигация: "< Назад" [1] [2] [3] "Далее >"

**Права видимости:**
- **User:** видит только инциденты, где он инициатор
- **Executor:** свои созданные + инциденты своего отдела (где он в поле department_id)
- **Manager:** все инциденты своего отдела + может видеть все
- **Admin:** все инциденты

**Быстрые действия (кнопки в строке):**
- "Взять в работу" (для Executor, если статус "Новый" и инцидент в его отделе)
- "Назначить" (для Manager/Admin, если нужно переназначить конкретному исполнителю)
- Индикатор непрочитанных комментариев (оранжевый кружок с числом)

- [Добавить комментарий]
- [Прикрепить файл]

- [Взять в работу] (основная кнопка)
- [Добавить комментарий]
- [Прикрепить файл]

Для **Executor (исполнителя)** при статусе "В работе":
- [Отметить как решённый] (зелёная кнопка)
- [Добавить комментарий]
- [Прикрепить файл]

Для **Manager/Admin** (всегда):
- [Назначить исполнителя] (если не назначен)
- [Сменить исполнителя] (если назначен)
- [Изменить приоритет] — **с автоматическим пересчётом дедлайна**
- [Изменить статус]
- [Изменить категорию]
- Все действия других ролей

**Изменение приоритета:**

При изменении приоритета система:
1. Определяет, был ли приоритет повышен или понижен
2. Если приоритет **повышен** (например, Средний → Критический):
   - Пересчитывает дедлайн SLA по новым правилам
   - Добавляет запись в историю: "Приоритет повышен: Средний → Критический. Дедлайн пересчитан: было X, стало Y"
   - Отправляет уведомление исполнителю о срочности
3. Если приоритет **понижен**:
   - Дедлайн остаётся прежним (опционально, можно настроить пересчёт)
   - Добавляет запись в историю: "Приоритет понижен: Высокий → Средний"

### 1.4. Взятие инцидента в работу
**Доступ:** Executor (только инциденты своего отдела)

**Условия:**
- Статус инцидента "Новый"
- Инцидент направлен в отдел исполнителя
- У исполнителя нетConflicting задач (опционально)

**Логика при взятии в работу:**
1. Executor нажимает кнопку "Взять в работу"
2. Система меняет статус "Новый" → "В работе"
3. Записывает ID исполнителя в incident.executor_id
4. Фиксирует дату взятия в работу
5. Добавляет запись в IncidentHistory: "Исполнитель [ФИО] взял инцидент в работу"
6. Отправляет уведомления:
   - Инициатору: "Инцидент #123 взят в работу"
7. Перенаправляет на страницу инцидента

### 1.5. Назначение конкретного исполнителя (опционально)
**Доступ:** Manager, Admin

**Когда используется:**
- Manager хочет закрепить инцидент за конкретным сотрудником
- Нужно переназначить на другого исполнителя

**Модальное окно:**
```
┌────────────────────────────────────────┐
│ Назначить исполнителя                  │
│                                        │
│ Текущий отдел: IT-поддержка            │
│                                        │
│ Выберите исполнителя из отдела:        │
│ ┌────────────────────────────────────┐ │
│ │ ▼ Петров П.П. (5 активных)        │ │
│ │   Сидоров С.С. (2 активных)       │ │
│ │   Козлов К.К. (8 активных)        │ │
│ └────────────────────────────────────┘ │
│                                        │
│ Комментарий (опционально):             │
│ ┌────────────────────────────────────┐ │
│ │ Срочно, пользователь ждёт          │ │
│ └────────────────────────────────────┘ │
│                                        │
│     [Назначить]     [Отмена]          │
└────────────────────────────────────────┘
```

**Логика при назначении:**
1. Manager/Admin выбирает исполнителя из списка сотрудников отдела
2. Опционально пишет комментарий
3. Нажимает "Назначить"
4. Система меняет статус "Новый" → "Назначен"
5. Записывает ID исполнителя в incident.executor_id
6. Фиксирует дату назначения
7. Добавляет запись в IncidentHistory
8. Отправляет уведомления:
   - Исполнителю: Email + Telegram + внутреннее "Вам назначен инцидент #123"
   - Инициатору: внутреннее "Инциденту назначен исполнитель"
9. Закрывает модальное окно, обновляет страницу

**Возможные переходы:**
- Новый → В работе (Executor берёт в работу напрямую)
- Новый → Назначен (Manager/Admin назначает конкретного исполнителя)
- Назначен → В работе (назначенный Executor начинает работу)
- В работе → Решён (Executor решил)
- Решён → Закрыт (User подтверждает)
- В работе → Ожидание (Executor запрашивает информацию)
- Ожидание → В работе (получен ответ)
- Решён → В работе (переоткрытие при отказе)

**Флаг просрочки (overdue):**
- Устанавливается автоматически при превышении дедлайна SLA
- НЕ меняет текущий статус инцидента
- Отображается визуальным индикатором в UI

**Модальное окно смены статуса:**
```
┌────────────────────────────────────────┐
│ Изменить статус                        │
│                                        │
│ Текущий статус: В работе               │
│ Новый статус:   ▼ Решён                │
│                                        │
│ Комментарий (обязательно):             │
│ ┌────────────────────────────────────┐ │
│ │ Принтер подключён к сети,          │ │
│ │ выполнена перезагрузка,            │ │
│ │ тестовая печать прошла успешно     │ │
│ └────────────────────────────────────┘ │
│                                        │
│     [Подтвердить]     [Отмена]        │
└────────────────────────────────────────┘
```

**Логика:**
1. Пользователь выбирает новый статус
2. Заполняет обязательный комментарий
3. Нажимает "Подтвердить"
4. Система меняет статус
5. Фиксирует соответствующую дату (для "Решён" - дата решения, для "Закрыт" - дата закрытия)
6. Добавляет запись в IncidentHistory
7. Создаёт системный комментарий в инциденте
8. Отправляет уведомления заинтересованным сторонам

### 1.6. Добавление комментариев
**Доступ:** Все роли

**Функционал:**
- Текстовое поле с поддержкой форматирования (жирный, курсив, списки)
- Чекбокс "Внутренний комментарий" (только для Executor/Manager/Admin)
  * Если включён → комментарий видят только специалисты
  * Если выключен → видят все участники инцидента
- Кнопка "Отправить комментарий"

**Логика:**
1. Пользователь пишет текст (минимум 3 символа)
2. Опционально отмечает как внутренний
3. Нажимает "Отправить"
4. Система сохраняет комментарий в таблицу Comment
5. Обновляет блок комментариев на странице через AJAX
6. Отправляет внутренние уведомления:
   - Инициатору (если комментарий публичный и он не автор)
   - Исполнителю (если он не автор)
   - Всем, кто писал комментарии ранее (участники переписки)

### 1.7. Прикрепление файлов
**Доступ:** Все роли (пока инцидент не закрыт)

**Интерфейс:**
- Drag-n-drop зона: "Перетащите файлы сюда или нажмите для выбора"
- Или кнопка "Прикрепить файл"
- Превью выбранных файлов перед загрузкой
- Прогресс-бар при загрузке

**Ограничения:**
- Максимум 5 файлов на один инцидент
- Размер каждого: до 10 МБ
- Типы: jpg, png, pdf, doc, docx, txt, log, zip

**Логика загрузки:**
1. Выбор файла пользователем
2. Валидация: тип, размер, общее количество
3. Загрузка на сервер в папку `/attachments/{incident_id}/`
4. Сохранение записи в таблицу Attachment
5. Создание системного комментария: "Пользователь {ФИО} прикрепил файл {имя}"
6. Обновление блока вложений

**Скачивание:**
- Клик по имени файла → автоматическое скачивание
- Проверка прав доступа перед отдачей файла

**Удаление:**
- Доступно только автору или Admin
- Модальное окно: "Удалить файл {имя}?"
- При подтверждении: удаление с сервера + из БД + системный комментарий

### 1.8. Закрытие инцидента
**Доступ:** User (инициатор) или Manager/Admin
**Условие:** Статус должен быть "Решён"

**Модальное окно:**
```
┌────────────────────────────────────────┐
│ Закрыть инцидент                       │
│                                        │
│ ✓ Проблема решена полностью?          │
│                                        │
│ Оцените работу исполнителя:            │
│ ★ ★ ★ ★ ★  (кликабельные звёзды)       │
│                                        │
│ Комментарий (опционально):             │
│ ┌────────────────────────────────────┐ │
│ │ Спасибо, всё работает              │ │
│ └────────────────────────────────────┘ │
│                                        │
│     [Закрыть инцидент]    [Отмена]    │
└────────────────────────────────────────┘
```

**Логика:**
1. Инициатор подтверждает решение проблемы
2. Ставит оценку (опционально)
3. Пишет комментарий (опционально)
4. Система меняет статус на "Закрыт"
5. Фиксирует дату закрытия
6. Сохраняет оценку (если была)
7. Добавляет запись в историю
8. Отправляет уведомление исполнителю: "Инцидент #123 закрыт. Оценка: 5/5"
9. Инцидент становится read-only (нельзя редактировать)

## 2. МОДУЛЬ: АВТОМАТИЧЕСКИЙ КОНТРОЛЬ SLA

```

**Форма добавления/редактирования:**
```

│ Приоритет: ▼ Критический               │

- Низкий → 72 часа

### 2.2. Автоматический расчёт дедлайна

**Выполняется при создании инцидента:**

Алгоритм:
```python
# 1. Получить приоритет инцидента
priority_id = incident.priority_id

# 2. Найти SLA-политику для этого приоритета
sla_policy = SlaPolicy.query.filter_by(priority_id=priority_id).first()

# 3. Если политика есть, взять время из неё, иначе 24 часа по умолчанию
resolution_time_hours = sla_policy.resolution_time if sla_policy else 24

# 4. Вычислить дедлайн
deadline = incident.created_at + timedelta(hours=resolution_time_hours)

# 5. Сохранить в БД
incident.sla_deadline = deadline
```

**Особенности расчёта SLA:**

**1. Учёт рабочих часов:**
- Рабочее время: 9:00-18:00 (9 часов в день), понедельник-пятница
- Выходные и праздничные дни НЕ учитываются
- Если инцидент создан вне рабочего времени — SLA начинается с начала следующего рабочего дня

**Примеры:**
| Время создания | Приоритет | SLA | Дедлайн |
|----------------|-----------|-----|---------|
| Пн 10:00 | Высокий (8ч) | 8 рабочих часов | Пн 18:00 |
| Пт 17:00 | Критический (4ч) | 4 рабочих часа | Пн 12:00 |
| Сб 14:00 | Средний (24ч) | 24 рабочих часа | Ср 18:00 |
| Вт 16:00 | Низкий (72ч) | 72 рабочих часа | Чт следующей недели 18:00 |

**2. Пересчёт при изменении приоритета:**
- При повышении приоритета дедлайн пересчитывается автоматически
- При понижении приоритета — дедлайн остаётся прежним (опционально)
- В историю добавляется запись: "Приоритет изменён, дедлайн пересчитан"

**Алгоритм расчёта дедлайна с учётом рабочих часов:**
```python
from datetime import datetime, timedelta

def calculate_sla_deadline(created_at, sla_hours):
    """
    Рассчитывает дедлайн SLA с учётом рабочих часов.
    Рабочее время: 9:00-18:00, пн-пт
    """
    WORK_START = 9   # 9:00
    WORK_END = 18    # 18:00
    WORK_HOURS_PER_DAY = WORK_END - WORK_START  # 9 часов
    
    current = created_at
    remaining_hours = sla_hours
    
    while remaining_hours > 0:
        # Пропускаем выходные
        if current.weekday() >= 5:  # 5=сб, 6=вс
            current = current.replace(hour=WORK_START, minute=0)
            current += timedelta(days=1)
            continue
        
        # Определяем начало и конец рабочего дня
        work_day_start = current.replace(hour=WORK_START, minute=0, second=0)
        work_day_end = current.replace(hour=WORK_END, minute=0, second=0)
        
        # Если текущее время раньше начала рабочего дня
        if current < work_day_start:
            current = work_day_start
        
        # Если текущее время после конца рабочего дня
        if current >= work_day_end:
            current = work_day_start + timedelta(days=1)
            # Переход на следующий день с проверкой на выходные
            continue
        
        # Сколько часов осталось до конца рабочего дня
        hours_left_today = (work_day_end - current).total_seconds() / 3600
        
        if remaining_hours <= hours_left_today:
            # Дедлайн сегодня
            return current + timedelta(hours=remaining_hours)
        else:
            # Переходим на следующий рабочий день
            remaining_hours -= hours_left_today
            current = work_day_start + timedelta(days=1)
    
    return current
```

### 3.2. Автоматическая эскалация уровня 1

**Фоновая задача (каждые 5 минут):**

```python
# 1. Получить активное правило эскалации уровня 1
rule = EscalationRule.query.filter_by(level=1, active=True).first()

if rule:
    # 2. Выбрать инциденты в работе
    incidents = Incident.query.filter(
        Incident.status.in_(['Назначен', 'В работе'])
    ).all()

    for incident in incidents:
        # 3. Вычислить процент использованного времени
        total_time = (incident.sla_deadline - incident.created_at).total_seconds()
        elapsed_time = (datetime.now() - incident.created_at).total_seconds()
        percent = (elapsed_time / total_time) * 100

        # 4. Если >= 80% и эскалация ещё не была
        if percent >= 80 and not incident.escalated_level_1:
            # 5. Отметить факт эскалации
            incident.escalated_level_1 = True

            # 6. Добавить в историю
            history = IncidentHistory(
                incident_id=incident.id,
                previous_status=incident.status,
                new_status=incident.status,
                user_id=None,
                comment='Эскалация уровня 1: уведомление отправлено руководителям'
            )

            # 7. Отправить уведомления всем Manager
            send_escalation_level_1_notifications(incident)

            db.session.commit()
```

**Доступ:** Admin

```

│ ┌────────────────────────────────────────────────────┐ │
│ │ФИО           │Email        │Роль    │Статус│Акции │ │
│ ├──────────────┼─────────────┼────────┼──────┼──────┤ │
│ │Иванов И.И.   │ivanov@..    │User    │✓     │[✎][🗑]│ │
│ │Петров П.П.   │petrov@..    │Executor│✓     │[✎][🗑]│ │
│ │Сидоров С.С.  │sidorov@..   │Manager │✓     │[✎][🗑]│ │
│ │Козлов К.К.   │kozlov@..    │Admin   │✓     │[✎][🗑]│ │
│ └────────────────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────┘
```

**4 роли системы:**

1. **User (Пользователь)**
   - Создавать инциденты
   - Просматривать свои инциденты
   - Комментировать свои инциденты
   - Закрывать решённые инциденты

2. **Executor (Исполнитель)**
   - Всё, что может User
   - **Создавать инциденты** (как квалифицированный специалист)
   - Просматривать инциденты своего отдела
   - Брать инциденты в работу
   - Отмечать инциденты решёнными
   - Комментировать инциденты
   - Оставлять скрытые (внутренние) комментарии

3. **Manager (Руководитель)**
   - Всё, что может Executor
   - Просматривать все инциденты (или инциденты своего отдела)
   - Назначать исполнителей конкретным сотрудникам
   - Менять приоритеты и статусы
   - Просматривать отчёты и историю изменений

4. **Admin (Администратор)**
   - Полный доступ ко всем инцидентам
   - Управление пользователями и отделами
   - Управление справочниками
   - Настройка SLA и эскалаций
   - Удаление данных
   - Все отчёты
